## 实现与受测边界

管理页新增最多 10 个待完成任务的邮箱登录队列：录入邮箱、顺序请求验证码、用户提交对应验证码、核验真实身份、保存 Cookie。使用一个自有 Chrome 进程，每个账号建立独立 BrowserContext，完成后释放上下文。生成继续使用既有 Python 协议后端，不需要每个账号常驻浏览器。此实现仍通过官网浏览器登录；没有声称已实现无浏览器的纯 HTTP OTP。

当前固定 SDK 不包含邮箱 OTP 登录；旧 relogin 只是校验或刷新已有 Cookie。本轮补的是独立的凭据接入路径。验证码不写入队列 JSON、日志或 localStorage；认证 Cookie 只进入私密 Store。队列重启把未结束任务标为 INTERRUPTED，不自动再发验证码。认证成功只代表登录入池，不代表额度、文本、媒体或并发能力已验收。

入池前要求：独立上下文中的验证码页面回显邮箱匹配、muse.ai 的 hatch_sess 存在，以及服务端 Flight 中 isAuthenticated=true、viewerId 与 prelude.user.identifier 一致。账号用私密 Store 密钥的 HMAC 指纹去重。新账号的 Cookie、邮箱和指纹同一次 accounts 原子写入；已有账号更新受忙碌租约、unknown 隔离、活动操作和 credential revision 保护。传统 Cookie 导入记录没有身份元数据，不能据此证明与它们也已按上游身份去重。

本轮使用新 worktree、仓库外 HOME/Store/profile、localhost:18613，未复用 18611 或生产账号池运行数据。用户给出的邮箱和接码链接保存在仓库外；验收者通过获授权的收件箱读取本次验证码，产品本身不接收任意第三方收件箱 URL。原 18611 管理服务保留。

## 实际复现并修复的问题

1. **六位 OTP 会自动提交。** 官网当前公开组件在六位输入完成时调用 confirm-otp；旧驱动随后检查按钮，看到已经禁用或消失便过早返回 UNKNOWN。修复只输入一次，再等待认证结果，邮箱步骤仍最多一次显式点击。三项受控状态边界修前失败、修后通过；首个真实 UNKNOWN 保留。
2. **认证切页时本地只读超时过早结束。** 实号 trace 明确为 verify → snapshot → Runtime.evaluate 的 TimeoutError，identity_reloaded=false。旧版约 6 秒便退出，未走完原 45 秒观察窗口。修复仅在原窗口内继续只读 snapshot/Cookie/身份观察，不重置期限、不再次输入验证码或提交认证，单次可选官网 GET 也不会重复。六项定向边界验证通过；随后 8 个真实 Manager 登录连续完成。
3. **取消/关闭写盘失败会阻断清理。** 受控复现后，取消写失败回滚任务和内存验证码并唤醒；关闭写失败仍发停止信号并清理。无锁 request_stop 可打断浏览器等待，退出等待有上限。
4. **实际表单与保护边界。** 空 OTP 时 Next 本来禁用，不能当成发送中；英文“Log in or create an account”是正常联合标题，不能一概当注册拦截。独立注册、额外同意、CAPTCHA 等步骤仍 BLOCKED。浏览器临时目录删除前检查原归属、解析后的绝对路径、链接/联接与进程状态，不能清理日常 Chrome。

没有为取得成功而放宽身份断言、改旧 UNKNOWN 状态、清账本或重新生成。没有绕过 CAPTCHA、接受新账号条款或扩大权限。
